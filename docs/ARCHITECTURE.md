# Architecture

## Goal

The SAS RAG Assistant is a prototype for reusing SAS code across clinical trials. Given a new AdAM, listing, table, or figure requirement, it retrieves similar SAS snippets from prior synthetic studies and produces a near-ready code suggestion.

The design intentionally separates retrieval quality from generation. The prototype can run with the deterministic demo provider today, while the CodeLlama provider remains available for a future local model.

## High-Level System

```text
User
  -> CLI or FastAPI
  -> CodeRetriever
  -> EmbeddingGenerator
  -> ChromaDB vector search
  -> BM25 keyword search
  -> result merge and dedupe
  -> CrossEncoder reranker
  -> CodeGenerator
  -> demo provider or CodeLlama provider
  -> SAS code suggestion
```

## Main Components

### Corpus Loader

Location: `src/data/corpus_loader.py`

Responsibilities:

- Read `.sas` files from the configured corpus folder
- Create `CodeDocument` records
- Split SAS code into meaningful chunks
- Preserve metadata such as source file, code id, chunk id, line range, and chunk type

The chunker is SAS-aware. It tries to split around:

- DATA steps
- PROC SQL
- PROC SORT
- PROC MEANS
- PROC REPORT
- PROC FREQ
- Other PROC blocks
- SAS macros

This makes retrieval more useful than fixed-size text splitting because the assistant can return complete SAS blocks instead of arbitrary fragments.

### Embedding Generator

Location: `src/embeddings/embedding_model.py`

Responsibilities:

- Load the configured sentence-transformer model
- Embed corpus chunks during ingestion
- Embed user requirements during retrieval

Current model:

```text
intfloat/e5-small-v2
```

The project supports offline use once the model is cached locally with Hugging Face.

### Vector Store

Location: `src/embeddings/vector_store.py`

Responsibilities:

- Persist chunks in ChromaDB
- Store explicit embeddings generated by the embedding layer
- Query ChromaDB with explicit query embeddings
- Return stored documents and metadata for keyword retrieval

The ingestion path is:

```text
SAS files -> chunks -> embeddings -> ChromaDB
```

The retrieval path is:

```text
requirement -> embedding -> vector search -> candidate snippets
```

### Keyword Retriever

Location: `src/rag/keyword_retriever.py`

Responsibilities:

- Load all stored chunks from the vector database
- Score them with a local BM25-style keyword algorithm
- Return keyword matches that may be missed by pure semantic retrieval

Keyword retrieval helps with SAS-specific terms such as `ADSL`, `SAFFL`, `TRTEMFL`, `PROC REPORT`, `PARAMCD`, and `AVAL`.

### Hybrid Retriever

Location: `src/rag/retriever.py`

Responsibilities:

- Run vector retrieval
- Run keyword retrieval
- Merge results
- Remove duplicate chunks
- Preserve source labels such as `vector` and `keyword`
- Send a wider candidate set into reranking

This hybrid flow gives both semantic matching and exact clinical-programming term matching.

### Required Reranker

Location: `src/rag/reranker.py`

Responsibilities:

- Load the cross-encoder reranker
- Score each candidate against the original requirement
- Blend rerank score, vector similarity, keyword score, and SAS block usefulness into a final ranking

Current model:

```text
cross-encoder/ms-marco-MiniLM-L-6-v2
```

Reranking is a required part of the retrieval pipeline. If the reranker model is missing, API and CLI flows should return useful errors rather than silently pretending retrieval quality is complete.

### Code Generator

Location: `src/llm/code_generator.py`

Responsibilities:

- Retrieve top SAS snippets
- Build generation context
- Call the configured LLM provider
- Return a structured response with:
  - requirement
  - generated SAS code
  - retrieved snippets
  - similarity scores
  - rerank scores
  - assumptions
  - status

### LLM Providers

Locations:

- `src/llm/provider/demo_provider.py`
- `src/llm/provider/codellama_provider.py`

The current default is `demo`. It is deterministic and designed for a smooth prototype demo. It uses retrieved SAS code as the base and inserts requirement-specific logic where possible.

The CodeLlama path is preserved for the real local LLM route:

```text
./models/codellama-34b-instruct
```

Switching to CodeLlama is a config change once the model exists locally.

## Data Flow

### Ingestion

```text
1. CLI or app starts ingestion
2. CorpusLoader reads SAS files
3. SASCodeChunker creates structure-aware chunks
4. EmbeddingGenerator creates embeddings
5. VectorStore stores documents, metadata, ids, and embeddings in ChromaDB
6. Stats become available through CLI and API
```

### Retrieval

```text
1. User submits a requirement
2. Requirement is embedded
3. ChromaDB returns vector candidates
4. Keyword retriever returns BM25 candidates
5. Candidates are merged and deduplicated
6. Cross-encoder reranker scores candidates
7. Top snippets are returned with similarity, rerank, hybrid, and final scores
```

### Generation

```text
1. User submits a requirement
2. Retriever returns reranked SAS snippets
3. CodeGenerator builds the prompt/context
4. Demo provider or CodeLlama provider generates SAS code
5. Response includes generated code, retrieved snippets, assumptions, and status
```

## Interfaces

### CLI

Location: `src/cli/cli.py`

Supported commands:

```powershell
python -m src.cli.cli ingest --reset
python -m src.cli.cli stats
python -m src.cli.cli search --query "Create ADSL with safety flags" --top-k 3
python -m src.cli.cli generate --requirement "Create ADSL with safety flags" --top-k 3
```

### API

Location: `src/api/`

Supported endpoints:

```text
GET  /health
GET  /api/stats
POST /api/retrieve
POST /api/generate
```

The API is designed to return useful errors if required models or vector data are missing.

## Configuration

Main configuration lives under `src/core/config.py` and project config files.

Important defaults:

- Python: 3.11.9
- Embedding model: `intfloat/e5-small-v2`
- Reranker model: `cross-encoder/ms-marco-MiniLM-L-6-v2`
- Vector database: local ChromaDB
- LLM provider: `demo`

Recommended offline environment variables after model download:

```powershell
$env:HF_HUB_OFFLINE='1'
$env:TRANSFORMERS_OFFLINE='1'
```

## Error Handling

The prototype handles common failure modes:

- Missing vector database
- Empty retrieval results
- Missing Hugging Face model cache
- Missing local LLM model
- API request validation errors

The API should avoid raw crashes and return an actionable message where possible.

## Production Next Steps

The prototype demonstrates the concept well. A production-grade version should add:

- Real historical study corpus with access controls
- Study, domain, phase, therapeutic area, and sponsor metadata filters
- SAS linting and syntax validation
- Generated-code diffing against source snippets
- Review and approval workflow
- Audit trails for every retrieved and generated artifact
- Security model for protected clinical assets
- Evaluation set for retrieval accuracy and generation usefulness
